Decision: `MELETE_FLARESOLVERR_BEHIND_VPN` (Outside services → FlareSolverr → Already behind the VPN, off by default) says FlareSolverr already reaches sites through the VPN, as one sharing the VPN container's network does. With it on, pages for an indexer set to go through the proxy are fetched from FlareSolverr's own address, and it's never handed the proxy; off, such a page is still refused whenever the proxy can't be handed over (a login, an HTTPS proxy, a FlareSolverr before 3.2.0 or one that doesn't say it's FlareSolverr), never fetched direct. Every refusal now says what to do: turn the proxy off for that indexer, or mark FlareSolverr as behind the VPN. The README and `.env.example` say indexers that need FlareSolverr are best left off the proxy.

Why: FlareSolverr is never given a proxy's password, so an indexer needing it behind an authenticated proxy failed with nothing useful said. A solver in the VPN's network is already where the proxy would send it, so it can fetch for proxied indexers without the password going anywhere. The admin decides that the solver is behind the VPN; Melete can't check it. A VPN's exit addresses get much harder Cloudflare checks, which is why leaving those indexers off the proxy is the better default.
