Decision: The VPN for Melete's own traffic is Gluetun in a container (`compose.vpn.yaml`), which Melete reaches as an HTTP proxy (gluetun:8888, with a login) through the proxy settings, not WireGuard inside Melete. Melete manages it through Gluetun's control server only, with a key of its own (`MELETE_VPN_URL`, `MELETE_VPN_KEY`, the key sealed and never shown) from a roles file that gives slskd and Melete each a key and only the routes they need: it shows whether the tunnel runs, the public address and its country and the forwarded port, and starts, stops and restarts it. Melete's role has no `PUT /v1/vpn/settings`: that route merges any VPN setting (provider, endpoint, keys), so a key holding it could send the tunnel to a server of its holder's choosing; the server countries stay in Gluetun's own settings file. Before using a control server, Melete asks both routes it uses without a key (the start-and-stop one with a status Gluetun refuses, so nothing changes) and refuses the server unless each answers 401, as Gluetun's fallback role leaves routes open when no roles are set. Gluetun's proxy runs with `HTTPPROXY_STEALTH` on, so it adds no header naming Melete's address inside compose, and the example roles file's keys are empty, so an unedited copy doesn't start. Melete has no Docker socket, never reads Gluetun's settings back (they can hold the VPN's keys), and never holds the VPN's own keys, which stay in Gluetun's files. Gluetun's firewall keeps the tunnel's kill switch, and Melete's own proxy kill switch stays as it is.

Why: Gluetun is already pinned and in use for Soulseek, keeps the WireGuard keys and crypto out of Melete, and its firewall fails closed. Managing it through its control server gives admins the switches they need without giving Melete the host's Docker. Keys per role keep slskd and Melete each to what they use, and refusing an open control server keeps anyone else on its network from stopping the VPN.
