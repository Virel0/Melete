Decision: The VPN for Melete's own traffic is Gluetun in a container (`compose.vpn.yaml`), which Melete reaches as an HTTP proxy (gluetun:8888, with a login) through the proxy settings, not WireGuard inside Melete. Melete manages it through Gluetun's control server only, with a key of its own (`MELETE_VPN_URL`, `MELETE_VPN_KEY`, the key sealed and never shown) from a roles file that gives slskd and Melete each a key and only the routes they need: it shows whether the tunnel runs, the public address and the forwarded port, starts, stops and restarts it, and keeps chosen server countries (`MELETE_VPN_COUNTRIES`) by sending them to `PUT /v1/vpn/settings`, which in Gluetun 3.41.3 merges just that, checks it, and restarts the tunnel only when it changed; they're sent again every five minutes, as Gluetun forgets them when it restarts. A control server that answers a request without a key is refused, as Gluetun's fallback role leaves routes open when no roles are set. Melete has no Docker socket, never reads Gluetun's settings back (they can hold the VPN's keys), and never holds the VPN's own keys, which stay in Gluetun's files. Gluetun's firewall keeps the tunnel's kill switch, and Melete's own proxy kill switch stays as it is.

Why: Gluetun is already pinned and in use for Soulseek, keeps the WireGuard keys and crypto out of Melete, and its firewall fails closed. Managing it through its control server gives admins the switches they need without giving Melete the host's Docker. Keys per role keep slskd and Melete each to what they use, and refusing an open control server keeps anyone else on its network from stopping the VPN.
