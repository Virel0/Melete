Decision: Melete can serve HTTPS itself on an address of its own, beside plain HTTP, with a certificate and key read from PEM files and read again every 10 minutes when they've changed (a pair that doesn't load keeps the one in use; one that can't be read at start stops Melete starting, saying which file). It serves the same service over TLS 1.2 and 1.3 (rustls with aws-lc-rs, as the rest of the build), HTTP/1.1. A proxy in front may pass connections through as they are and name each client with a PROXY protocol header (v1 or v2), believed only from the proxies trusted for `X-Forwarded-For` and, once it's on, required of them; anyone else's header isn't read, so it fails as the TLS it isn't. The way in a request came by is still the proxy's, and over HTTPS the client is always what the listener decided (the header's client, else the connection's own address), never `X-Forwarded-For`, which on a connection passed through only the client could have written. Each connection has 5 seconds for its header, 10 for its handshake and 30 for each request's headers, and one where nothing is read or written for 60 seconds is closed (a body that never comes, a response nobody reads); at most 1,024 are open at once, and 64 for any one client. Certificates come from files for now; getting them from Let's Encrypt is a separate decision, since it sends the name to Let's Encrypt and every public certificate is listed in public logs.

Why: A reverse proxy that ends TLS itself reads everything that passes through it, so a VPS run by someone else could see what's watched and every sign-in. Ended at Melete, the VPS sees only that encrypted traffic flows, how much, and the name asked for. The PROXY protocol gives back the client's address, which a passed-through connection otherwise loses, for sign-in limits and the log.
